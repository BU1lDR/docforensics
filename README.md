# docforensics

Offline document forensics for a human investigator. A case of scanned and digital documents goes in. An investigation dossier comes out, and every finding in it is traced to a box on a page of a stored source file.

It is a solo entry by Aryan to the DataOps Innovation Hackathon 2026 (Hack The Core), for the problem statement on AI-powered document forensics and contextual intelligence.

The tool lists anomalies for a reviewer. It does not decide whether a document is authentic and it does not name intent. Observations, inconsistencies, candidates for closer review and limits of the analysis are kept apart, and what a finding means is the reviewer's decision. **Every document used to build and test it is synthetic:** read [docs/limitations.md](docs/limitations.md) before reading anything into a result.

## What it does

- **Several documents in one case.** PDF, PNG and JPEG, typed by their first bytes, limited in size, pages and number, hashed and stored read-only. A file that is refused or cannot be read becomes a visible limitation, not a crash.
- **Reading, offline.** The text layer of a digital PDF, or RapidOCR for a scan, gives every word a box. Scanned pages are classed by sharpness, because the recogniser's own confidence does not flag misread digits.
- **Understanding.** Each document is classified, and its fields and table cells are extracted with a confidence and a location. Bank statements, payslips and loan applications have a spec each (one drawn layout each). Document types are data, in TOML files; anything else is reported as `unknown`.
- **Visual and file forensics.** Digital PDFs: saved revisions, text covered by a shape or picture, hidden text, fonts of figures and dates, file metadata. Scans: image grain, the placement of words and the compression history of the JPEG picture. Across documents: the shape of the signature, of the logo and of the stamp, and whether a signature is the same image on two documents. In the stored bytes of every PDF, JPEG and PNG: bytes after the end of the file, a signature range that stops short of the end, embedded files and action keys (names only), an index that had to be rebuilt, an editor named in the picture's metadata.
- **Contextual intelligence.** Within a document: balance chain, totals, net pay against its words, dates, weekday. Across documents: name, address, employer, account number, net pay against the bank credit, declared income against earnings, the declared existing EMI against the instalments on the bank statement, dates, duplicate files, the same producing software. Two context rules against a synthetic reference.
- **Relationships between findings.** Findings that cite the same field, the same place on a page or the same name, address, employer or account are grouped. A group is ranked by how many independent kinds of check fired in it.
- **Entities across documents.** The names, addresses, employers and account numbers that the documents write are listed as entities (two writings share an entity only when the cross-document checks grade them as the same, or the same apart from form, and a writing joins an entity only if it grades so against every writing in it), with the places where each is written and the findings that touch it. Fixed rules on top of those checks, not a trained graph model; it finds no aliases and its accuracy was not measured.
- **An optional local model.** Off unless you ask for it. With `--llm`, a small model running on this computer words the headline of each group of findings, suggests relations, a summary and a reading order, and names the facts printed on a page of a type the tool has no spec for. A guard checks the first two before they are used; for the third, code checks that the words behind each named fact are on the page. The model cannot add, change or remove a finding, and everything it says is labelled as inference. See [The language model](#the-language-model).
- **Evidence you can follow.** Each finding names its document, page and box, with a marked crop. `trace` follows it to the stored file and checks the file against its sha256.
- **A dossier.** One self-contained HTML file and one JSON file: overview, extracted information, contextual analysis, visual forensic findings, evidence and traceability, investigation summary, and appendices with the audit trail, the capability matrix and the limitations.
- **A review desk.** A page in the browser on this computer for upload, page images with word, field and finding boxes, evidence, reviewer actions and the dossier download.
- **Reviewer decisions, counted.** What a reviewer decided about each finding (open, needs verification, confirmed by the reviewer or dismissed, with the note) is read back from the audit trail, after the chain and the signed checkpoints are checked, and counted per detector and class: with the `decisions` command, in the Dossier tab of the desk and as a JSON-lines download. These are counts of what a person decided, not accuracy figures, and nothing is fed back to the detectors.
- **An audit trail.** Every submission, step, failure, model use, dossier build and reviewer action is an event, each carrying the hash of the one before. At the end of a run and around the dossier build, the trail's length and last hash are also signed (Ed25519), and a reviewer action after that adds a checkpoint, so a trail that was changed and chained again, or cut short, no longer matches a checkpoint signed before. Nothing is signed on top of a trail or a checkpoint file that does not verify. `verify-audit` checks the chain and the signatures. A signature shows the trail's integrity only as far as the key stayed private and the checkpoint is still in the file; it says nothing about who held the key or when, and it is not a compliance claim.

How the pieces fit is in [docs/architecture.md](docs/architecture.md).

## Set up

Python 3.11 or newer. It was developed and tested on Windows 11 with Python 3.11.9; no other system has been tried.

```
git clone https://github.com/BU1lDR/docforensics.git
cd docforensics
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
pip install -e .
```

On a system other than Windows, activate with `source .venv/bin/activate`. Installing needs the internet once. After that nothing in the tool uses the network: the OCR models are inside the RapidOCR package, and the review desk answers on `127.0.0.1` only.

## Use

Analyse documents as one case. Each path is a file, or a folder (the files directly inside it):

```
python -m docforensics run statement.pdf payslip.pdf application.pdf
```

It prints the case id, the documents it recognised and the findings, and writes everything to `data/cases/<case id>/`, including `dossier.html` and `dossier.json`. `--data DIR` changes where cases are kept and `--config thresholds.toml` overrides the thresholds it names (the names are the fields of `Thresholds` in [config.py](src/docforensics/config.py); every finding prints the thresholds it used). In the benchmark, OCR took 1 to 2 seconds per A4 page at 200 dpi on a CPU-only laptop.

Open the review desk, then go to http://127.0.0.1:8000/ in a browser:

```
python -m docforensics serve
```

Upload the documents on the Documents tab. The Findings tab lists what was found, with the evidence, the explanation and the reviewer actions; the Clusters tab shows related findings together; the Relationships tab draws the names, addresses, employers and account numbers the documents write, with the findings that touch them; the Audit trail, Capabilities and Dossier tabs hold the rest. `--port` changes the port.

Follow a finding to its source, and check that the audit trail has not been changed:

```
python -m docforensics trace C-20261104-153000-ab12 F-003
python -m docforensics verify-audit C-20261104-153000-ab12
```

`trace` prints the document, the stored file and its sha256 (and whether the file still matches it), the page and the box in pixels and in PDF points, and the value read there.

`verify-audit` checks the hash chain first, then the signed checkpoints in `checkpoints.jsonl` in the case folder. It ends with `Signed:` (how many checkpoints, the id of the key, how far the last one reaches and how many later events no checkpoint covers) or `Unsigned:` (a case without a checkpoint, such as one made before signing existed, which passes with that note). A chain that fails, or a checkpoint that does not match the trail, prints what is wrong and exits with 1. The key is made by the first run, in `data/signing/` beside `data/cases/`, and the checkpoint carries its public half, so the key on its own proves little: whoever can change the trail can also reach the key in the same folder. The checkpoints are not linked to each other and live in the case folder, so the last ones can be deleted together with the events they cover, and the events after the last checkpoint can be replaced before the next action signs them; a copy of the `head` line, kept elsewhere, shows either, and a copy of a checkpoint shows the cut. To rely on a signature, keep a copy of `data/signing/public.pem` somewhere else (the file in `data/signing/` is rewritten from the key in use, so it is no check of its own) and give it when you check: `python -m docforensics verify-audit CASE --pubkey public.pem`. A case that is unsigned, or signed by another key, then fails.

Read back what a reviewer decided about each finding. The case id is optional: without it every case under `--data` is read.

```
python -m docforensics decisions C-20261104-153000-ab12
python -m docforensics decisions --tally
```

`decisions` prints one line of JSON per finding: the case, the finding, its detector and class, the status the reviewer left it in (`open` if nobody acted on it), the note, how many actions there were and the time of the last. `--tally` prints instead, per detector and class, how many findings were raised and how many stand at each status. The rows come from the audit trail, not from `case.json`, and only once the chain and the signed checkpoints verify as `verify-audit` checks them: a case that does not verify is named on stderr and left out, and the command ends with 1. The Dossier tab of the review desk shows the same counts and offers the rows as a download. Reading them adds nothing to the audit trail. The counts say what a person decided, not how well a detector works (a dismissed finding may be a false flag, or one the reviewer found beside the point), and nothing is learned from them; a threshold changes only when someone edits the TOML file by hand.

### Try it on the sample data

[sample_data/](sample_data/) holds eleven small cases. Eight are a bank statement, a payslip and a loan application of one fictional applicant: five of the development split (one genuine, three with a planted change that the tool finds, one with a planted change that it misses) and three of the `ext-dev` split of the reused-signature pack (one genuine, one with the same signature image on two documents that the tool finds, one with the same that it misses). The other three are single payslip scans of the `ext-dev` split of the compression-history pack (one genuine, one with a pasted field that the tool finds, one genuine scan that the check cannot examine). Run the first:

```
python -m docforensics run sample_data/dev-0000
```

It prints three findings: a closing balance changed in a later saved revision of the PDF, seen two ways (the earlier revision still holds the old text, and the transactions do not give the new balance), and the group that holds both. `run` ends with the command that follows a finding to its file. Use the case id and a finding id it printed:

```
python -m docforensics trace C-20261105-103000-ab12 F-001
python -m docforensics verify-audit C-20261105-103000-ab12
```

The date and time in a case id, in the audit trail and in the dossier are UTC. IST is UTC+05:30, so a run at 16:00 IST has 10:30 in its id. The dossier is `data/cases/<case id>/dossier.html`. One made from dev-0000 is kept as [sample_data/dossier-dev-0000.html](sample_data/dossier-dev-0000.html), with its data in [dossier-dev-0000.json](sample_data/dossier-dev-0000.json): open the HTML file in a browser after cloning, because GitHub shows only its source.

The five cases of the development split are from the split on which the thresholds were tuned, and the six `ext-dev` cases from the split on which the two newer checks were set up. They show the tool working from files to dossier; they are not evidence of how well it detects. The held-out figures are in [eval/test.md](eval/test.md); they are those of the tool at `spec-freeze` plus two fixes, not of the final tool (see Evaluation). Two of the eleven are misses: dev-0043 (a slightly changed logo) and ext-dev-h-0046 (a reused signature on 120 dpi scans). A third, ext-dev-e-0012, is a genuine scan whose last save is under quality 40: the compression-history check cannot examine such a picture, and the dossier does not say so (the capability matrix lists the limit). [sample_data/README.md](sample_data/README.md) says what the tool reports on each case, and `python -m pytest tests/test_e2e_sample.py tests/test_e2e_sample_packs.py` checks those statements against a real run.

## Demonstration documents

The `datagen/` package draws fictional bank statements, payslips and loan applications as PDFs whose content is known, applies one planted change to some of the cases (each change records what was done and where, in the pixel frame the tool reports) and simulates scans at several quality levels. Institutions carry TEST in their names; no real logo, person or identity document is used. The tests use it to check each detector against known truth. The generator's font-substitution manipulation reads Arial from the Windows fonts folder and does not run elsewhere. The tool does not use the generator.

The demonstration dataset is its output: a development split of 80 cases and a test split of 144, each case being one applicant's statement, payslip and loan application (a statement submitted twice adds a fourth file). In the test split 48 cases are genuine and 96 carry one change each, of twelve kinds: in a digital PDF an incremental edit, a cover retyped in the same font or in a near font, a metadata edit, a picture pasted over text; in a scan a paste from another scan, or text erased and retyped; across the documents a pay figure changed so that the payslip still adds up, a name, address, employer or month changed in one document, a statement submitted twice, a signature in another hand, another logo or stamp. A `manifest.json` per split holds the truth for every case. The test split is about 130 MB, so it is generated, not committed (from the repository folder; `data/` is not part of the repository):

```
python -m datagen.build test data/test-split --cases 144
```

## Evaluation

The figures below come from `python -m evaluation.run_eval --split dev` and `--split test`. Their reports are committed as they were written: [eval/dev.md](eval/dev.md) for the development split and [eval/test.md](eval/test.md) for the test split. Each one states how a result is counted, lists every miss and every flag on a genuine document, and ends with the limits of its measurement. They name the machine as Windows 10, which is how Python's platform module names this Windows 11 build (10.0.26300). The test report describes the tool at `spec-freeze` plus two later fixes. The development report was made again on 7 November at commit 06b39ed, the tool as it stood then; its first report, 50 of 54 changes found, is in the history. What was added after the test run, and what has not yet been run on a held-out split, is at the end of this section.

**How it was run.** The detectors were written and their thresholds set on the development split (80 cases, one drawn layout, "A"). The test split (144 cases, layouts A and B) was generated and run once, after the code was frozen (git tag `spec-freeze`, commit 28ef833), and nothing was changed in response to its results. It holds what development never showed: a second layout, "B", drawn after the extraction specs were final, and two kinds of change (a cover retyped in a near font, a scan erased and retyped). One defect in label matching, found by reading layout B once on digital drawings before the test split was built, was fixed; eval/test.md says so. A change counts as found when the tool raised an observation, an inconsistency or a potential-manipulation finding on the changed document, at the changed place where the change has one. A limitation ("could not be checked") is never a find. A finding on a genuine document is a flag.

- Document type recognised: 440 of 440.

**What these figures do not show.**

- They are about synthetic documents drawn by one generator. The two splits share its six logo and stamp designs and its lists of names, addresses and employers. Nothing is measured on real documents, scanners or layouts.
- The extraction specs list the wordings of labels, column headings and captions of layout A. Layout B uses other wordings for about half of them, and it is read far worse than A (no id, 34 % of the text on digital pages). Whatever depends on a value that is not read is left unchecked; for every genuine statement and payslip of layout B the within-document checks said so.
- 8 cases per kind of change is a small sample, and one run. A difference of one or two cases between kinds of change means little. The overall 82 % is a count over this particular mix of changes, not a property of the tool: it is 58 of 60 on digital files and 21 of 36 on scans.
- The flag rate of 1 in 144 holds for clean synthetic documents. Real genuine documents differ in more ways, and the ordinary causes of each finding are in [docs/limitations.md](docs/limitations.md).
- The obligations rule is not tested on genuine documents (the generator holds obligations to 40 % of income), the grouping of findings is not scored, and no language model took part in the evaluation.

No accuracy is claimed beyond these figures. A document with no finding is not thereby shown to be unchanged, and a finding is a lead for a reviewer.

**To repeat it.** The run takes about 20 minutes on the laptop and, like the generator's near-font cover, needs Windows with Arial. `--out` keeps it from overwriting the committed reports:

```
python -m evaluation.run_eval --split test --out data/eval-test
```

The report records the commit it ran on and whether the working tree had changes. The test split was run once, at `spec-freeze`. Two fixes followed, before the later work described below. `pdf_overlay.py` and `pdf_fonts.py` put the evidence boxes of a PDF page stored turned (`/Rotate`) in the wrong frame. `understand/layout.py` and `read/__init__.py` read a page that stands on its side (a scan or a PDF page turned a quarter turn) as poor quality, because such a page gave false conflicts between documents; one sentence in `checks/within.py` was reworded to match. Neither change was prompted by a result on the test split: the first came from reading the code against a list of inputs the tests did not cover, the second from trying turned pages on development cases. Neither split holds a turned page. [Limitation 36](docs/limitations.md) says what is still not handled. After these two fixes both splits were run again, from a copy of that source: every count was the same as in the reports committed then (test split 79 of 96 found and 1 flag on 144 genuine documents; development split 50 of 54 and none on 78), and only the times differ. Those two reports say "commit unknown" because the copy had no git history, and they are not kept.

**These figures are not the final tool's.** Nine features were added after those runs: template-free extraction with the local model, an entity relationship view, signed audit checkpoints, a check of a scan's JPEG history, detection of a signature reused on two documents, a check of the raw file structure, a learned word check on scanned pages, a check of the declared existing EMI against the bank statement and counts of reviewer decisions. `git diff spec-freeze HEAD -- src requirements.txt` shows the whole change to the tool. None of the held-out figures above, the times included, covers them. The development report made again at 06b39ed was run without the language model and has the other five checks that read or detect something in it, as development data. The six that read or detect something (the model's extraction, the JPEG-history check, the reused-signature check, the raw file-structure check, the learned word check and the declared-EMI check) have development figures only, and their rows in the capability matrix name the data the figures come from; the relationship view, the signed checkpoints and the reviewer-decision counts add no finding of their own and have no accuracy figure. The test split and a second held-out split, built for the new checks, are to be run once on the frozen final code (git tag `freeze-2`), and both runs will be reported here. Until then the figures above are the only held-out figures this README claims.

**Raw file structure.** Besides what a page shows, the tool reads the stored bytes of every PDF, JPEG and PNG and reports facts about the file itself (`src/docforensics/forensics/structure.py`), each as an observation with a byte offset or object number and at most 32 bytes shown as hex and ASCII: bytes after the last end-of-file marker of a PDF or after the end of a picture (also for the JPEG pictures inside a PDF); an /Info record that differs from the XMP packet; a signature byte range that stops short of the end of the file or runs past it; embedded files and the names of action keys (/JavaScript, /JS, /OpenAction, /AA, /Launch), never opened or run; a file whose index had to be rebuilt to be read; an image-editor name in picture metadata and an EXIF save time later than the time taken. It is not a malware scanner and does not check any signature's cryptography (a signed PDF carries a limitation saying so), and ordinary files carry the same facts. It was measured on 120 files that the same author built for the purpose with `datagen/structure_pack.py` (60 untouched, 60 with one planted change): no observation on the untouched ones, all 80 expected observations on the others, none unexpected ([report](eval/structure/ext-dev.md)). Those figures are by construction: they show what the check does with the changes it was written for, are not a detection rate, and say nothing about files made by other programs.

**Learned word check.** One scan check is fitted to data instead of written by hand (`src/docforensics/forensics/learned_patches.py`; the weights are `learned_patches.json`, made by `evaluation/train_patches.py` with numpy only, no new dependency). For each word of a scanned page it takes fourteen measures against the rest of the page (grain, edges, strokes, ink, JPEG block grid, baseline, placement, and how far the word sits off the line of its neighbours) and weighs them with a logistic regression fitted to synthetic edits from the project's own generator (295 development cases, 46,290 words, 319 inside an edit; the test splits were not used). Words whose score reaches a limit fixed on development data are listed in one observation per page, each with its box, its score and the three measures that raised it most; the score is not a probability. The bar it had to meet was written into the training script before the first model was fitted, and it went in because it met it on pages held out from fitting: 16 of 36 pages with a part of another scan pasted in against 3 for the grain and placement checks, and 59 of 72 pages of the compression-history pack against 19, with none of 195 unedited pages flagged ([report](eval/patches/acceptance.md), [design record](eval/patches/design.md)). Its weak points are in the same report: retyped amounts are found 12 of 18 times where the grain and placement checks find 18 of 18, most of the gain on pasted-in parts rests on two hand-written alignment measures, and the figures are by construction, since the generator, the edits and the check have one author. They show that these edits are found, not that edits made by anyone else would be. A page that carries no scanner grain, such as one printed or rendered to an image, is not given to it (nor to the grain and placement checks); the document gets one limitation that says so.

**Declared existing EMI.** A loan application declares the applicant's existing EMI, and the bank statement shows what is debited. The check (`check_emi` in `src/docforensics/checks/cross.py`) adds up, for each calendar month, the debits whose narration holds the whole word EMI, instalment or loan and no word that makes it a fee, a reversal or a closing payment, and when the month with the most exceeds the declared figure by more than 10 % of those instalments it reports an inconsistency that cites the declared figure and each debit with its narration. A declared figure above the instalments is not reported, and a comparison that cannot be made (the figure, an amount, a date or a narration unreadable, or a page of poor quality) is a limitation, never a pass. It was measured on 44 cases that the same author built for the purpose with `datagen/emi_pack.py` (an application and a statement each; digital and scanned; layouts A and B): no finding on the 28 cases with nothing to find; the 6 planted gaps of layout A found, each with the right total; none of the 6 of layout B, because the statement reader does not list the heading 'Narration' (on purpose: layout B is the test of unseen wording) and so reads no narration there, which the dossier says on all 22 layout-B cases of the pack instead of passing them; none of the 4 gaps hidden behind a lender's name alone, as expected ([report](eval/emi/ext-dev.md)). The first run ([report](eval/emi/ext-dev.first-run.md)) found the same 6 and said nothing about the 6 it missed; that statement was added after the result was seen, so the second run does not measure the reading independently of the fix. The figures are by construction, from one generator, and say nothing about real statements.

**A probe on documents printed by another program.** 24 synthetic cases (a bank statement, a payslip and a loan application each) were written as HTML and printed by headless Edge, a producer the tool was not built around, and then changed: 588 edits of digital files and 108 of scanned pages ([docs/probe.md](docs/probe.md); one row for each edit in the [record](eval/probe/digital.csv)). Of the 500 digital edits that a check was expected to see, 473 were found and 413 pointed at the edited place. The 88 edits written down beforehand as expected misses (a halved declared EMI, a producer name that is not on the metadata check's list, an incremental save with nothing visible, a debit changed with the balances carried through, a loan amount) were not found, and neither were 27 others. Most of those 27 are two kinds of edit that leave the edited document adding up (a net pay raised through the tax deduction, a credit with the later balances carried through): they were found in only half of the cases, because the comparison with the other document needs the pay date, which the grid payslips label 'Paid On' and the tool does not read. No edit made a new finding that cites only documents that were not edited. 88 of the 108 scanned edits were found, and none of the 18 unedited scanned controls carries a finding that is more than a limitation line (one of them carried a false balance inconsistency until a transaction row that the reader had left out was read). The tool was changed four times after the first look at these same cases (the extraction of values from the three documents, a reader for a Dr/Cr column, a gate that keeps the scan checks off printed pages without scanner grain, and the table row), so this is development data: it shows what the current build does with these 24 cases, not what it does with anybody else's documents, and no held-out split was used.

## Capability matrix

Each capability is marked Implemented, Partial, Planned or Unsupported. The table is written from [capabilities.json](src/docforensics/capabilities.json), the file the dossier and the review desk print. After that file changes, rebuild this table with `python -m docforensics.capabilities --update` from the repository folder.

## Limitations

The full list of limitations and assumptions, and a table of the ordinary things that raise each finding, is in [docs/limitations.md](docs/limitations.md). In short:

- Nothing was evaluated on real documents, real scanners or real layouts.
- Extraction is tied to the wordings of labels that the specs list. On a layout that words them differently, values are reported missing and the checks that need them are not made, and the tool says so (held-out layout B: no id read, 34 % of the text on digital pages).
- On scans the tool found little: 6 of 16 pasted or retyped scans, and 2 of 9 changes at 120 dpi. A scan with no finding says little about whether it was changed.
- A finding is a measurement for a reviewer, with the ordinary causes of the same result written next to it. The tool never concludes anything about authenticity or intent.
- Files are opened by PDF and image parsers in the same process as the tool. Limits on size, pages and time apply, and there is no sandbox.
- A check that cannot run is reported as not checked. It is never reported as clear.

## The language model

A local language model is optional, and it is off unless you ask for it. Nothing depends on it: extraction by the specs, the detectors, the checks across documents and every number in the dossier come from code, and the reports in eval/ other than eval/x/ are produced without a model. Digits, arithmetic and revision differences are never left to a model.

```
ollama pull phi4-mini:3.8b
python -m docforensics run statement.pdf payslip.pdf application.pdf --llm
python -m docforensics serve --llm
```

`ollama pull` needs the internet once; after that the model runs offline. With `--llm`, a small model (phi4-mini 3.8B, MIT) runs through Ollama on this computer and does three things, and only these: it words the headline of each cluster of findings; it reads the case once and suggests relations between findings, a short summary and an order to read them in; and, for a page whose type has no spec, it names the facts the page states, each with the words it took the value from (template-free reading, see its row in the capability table). `--llm-model NAME` picks another model Ollama has; qwen3-4b-instruct-2507 was measured too. If Ollama is not running or does not have the model, the run stops before a case is made and says what to do. If a call fails during a run, the template wording stays and the audit trail says why.

- **What it sees.** For the headlines and the reading of the case: structured findings (ids, kinds of check, titles and the values the checks used), never page text, a finding's detail or a box. For template-free reading: the first 60 lines of text of the first 2 pages of a document whose type has no spec, as numbered lines, never boxes or images. The client talks to `127.0.0.1` only and refuses any other host; no hosted service is used at run time.
- **What it cannot do.** Add, change, confirm or remove a finding. It adds, ranks and explains.
- **What is kept.** A guard judges the summary and each relation apart. Ids must be ones it was given, figures and dates must be ones the findings hold, verdict words are refused, and a relation's kind must be true of what its two findings cite. What fails is dropped, and the dropped part is kept with the reading and shown as dropped. The order can only rank: every finding stays in it once, and a finding the model leaves out follows in the tool's own order.
- **How it is shown.** "AI-generated wording (inference)" on a headline. "AI reading of the case (inference)" in the dossier's investigation summary and in the review desk's Clusters tab. Every call is an audit event with the model, its digest, the hashes of what went in and came out, and the verdict.
- **What was measured.** On development-set prompts, CPU only, one run each: the guard accepted 18 of 24 headline wordings from phi4-mini (13 of 24 from qwen3), and a call took 17 to 26 s on average for a headline and 40 to 48 s for a reading (figures and sources in `docs/spike.md`). The guard checks ids, figures, dates and verdict words, not meaning, so wording it accepts can still be wrong; limitation 30 in [docs/limitations.md](docs/limitations.md) gives examples. Nothing was run with a model on the held-out split.
- **For a demo.** A case takes a minute or more with the model, and free RAM falls to about 2 GiB. Use three or more documents: the stage has 120 s per document plus 120 s, and a call starts only if it fits in what is left. Template-free reading adds a call of 60 to 123 s for each page it reads (at most 2 pages of a document); that stage has 120 s per document plus 120 s, and once a call fails the rest of that case is not read.

The design is in [docs/architecture.md](docs/architecture.md).

## Data

Everything used here is synthetic: fictional people and institutions, no real customer, logo or identity document. If you run real documents through the tool, you need the right to. A case is kept as plain files under `data/` (originals, page images, crops, extracted values, findings, audit trail and its signed checkpoints), without encryption or user accounts, and `data/` is not part of the repository. The key that signs the checkpoints is one more plain file, `data/signing/private.pem`, with no password; copy a case folder without that folder when you share it.
